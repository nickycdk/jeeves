# Changelog

## Unreleased (0.3)

- Auto-start runs (ST-13.3 … ST-13.9; release notes draft: `docs/release-notes/v0.3.0.md`). On a new install, an interactive session in a git repository, on a model with a window above 200K tokens, in a fresh conversation, is watched by itself: the first typed prompt becomes the task (`auto`; `/jeeves on` tasks are `explicit`). A notice once, before anything is recorded. Auto tasks: no handover in the first 3 turns; end when the first reading is already near the threshold, on a switch to a 200K model, and on a `/clear` you type (explicit tasks still pause); recover by themselves after a session closed mid-handover; deleted 7 days after they ended without a handover. `/jeeves on <goal>` makes an auto task explicit. `/jeeves status` shows `(auto)`/`(explicit)` and, for a session that is not watched, why. `/jeeves later` postpones a handover by 10 points up to a cap. New handovers carry a Current goal, shown in the rotation line; the continuation gives the user's own words first. README and PRIVACY.md describe all of it.
- A message typed during a handover is no longer quoted in `events.jsonl` (the line names it by its length); it was kept there after delivery, against NFR-10 and PRIVACY.md.
- A session that is not auto-watched only because of the upgrade default, a resumed conversation, no git or a 200K window gets one hint at the point a watched one would be warned (ST-14.1): once per session, never under `-p` or after any off, silent after 3 unanswered (count kept in the plugin store, reset by a typed `/jeeves on` or `/jeeves auto on`). No files, no tokens.
- `/jeeves` alone (and `/jeeves status`) ends with a `Try:` line of the commands that fit now (ST-14.2): `later | off` during the warning, `resume | off` when paused, `retry | off` after a failed handover while retries are left, `on` when the session is not watched, then `help`. It stays within 8 lines; the folder path now gives way first more often.
- Test runs only (ST-15.1, for AC-41's simulated 200K run): `JEEVES_TEST=1` with `JEEVES_TEST_WINDOW_OVERRIDE=<tokens>` makes a session behave as one with that window (eligibility, the threshold default, readings re-based on it); `/jeeves status` then says `TEST OVERRIDE window 200K`.
- Tests: the mod suite runs twice, with the `/config` row `autoStart` off (`npm run test:mod`) and on (`npm run test:mod:on`), in CI too.
- Auto-start settings (ST-13.2; nothing starts by itself yet): `/jeeves auto` shows whether auto-start is on and which setting decided it; `/jeeves auto on|off` sets it everywhere (in `auto.json`, never in Claude settings); `/jeeves defaults auto on|off` sets one project; `/jeeves off` keeps it off for the rest of the session; a `/config` row `Auto-start` (`default`, `on`, `off`) wins over `/jeeves auto` when set. Precedence: session, project, `/config`, `auto.json`, then the install. The first 0.3 session checks once whether 0.2 was used here (its notice was shown, or a project exists): if so, auto-start stays off and Jeeves says once how to turn it on. The first `/jeeves on` notice is now remembered under its own key.
- State files for auto-start (ST-13.1): a task records whether it started by `/jeeves on` or by itself (`state.json` schema 2; 0.2 tasks read as started by `/jeeves on`), a project's `config.json` can hold `autoStart`, and a new `auto.json` in the state folder holds the setting for everywhere. **Going back to 0.2:** 0.2 refuses a task that 0.3 has touched ("update Jeeves") and never rewrites it; it ignores a project `config.json` only when `autoStart` is set there (every other one keeps its threshold and checks), and never reads `auto.json`. No data is lost either way.

## 0.2.0 (release candidate; dated when tagged)

Release notes: `docs/release-notes/v0.2.0.md`.

- Jeeves notices when a plugin above it skips its Stop hook (on Claude Code 2.1.319, accounts in a Team organization get a built-in security plugin, `cc-plugin-sec-default`, that does this): after the first answer that ends without the hook, it switches to `unsupported`, shows `off: Stop hook skipped`, explains once, and refuses `/jeeves on`. Without that hook it cannot hand over at all.
- `/jeeves status` keeps the reason and the defaults warning when there is more to show than 8 lines; the folder path and last handover give way first.
- The `/jeeves` command menu lists every command (`done`, `retry`, `defaults`, `stats` and `history --full` were missing).
- A new task hands over at 40% when the model's context window is larger than 200K tokens (for example 1M), and at 50% otherwise or when the window is unknown. Chosen once when the task starts; `/jeeves threshold` still overrides it. `/jeeves status` shows the threshold in tokens too (`Threshold: 40% (~400K)`).
- `/jeeves defaults`: per-project defaults for new tasks, `defaults threshold <n>` and `defaults check <cmd>` (up to 20), `defaults clear`. `/jeeves on` copies them into the new task (checks as task revisions, so `/jeeves task` shows them); running tasks are not changed. Kept in the state folder (`projects/<project>/config.json`); an unreadable file is ignored and `/jeeves status` says so. `/jeeves purge --project` deletes it.
- When a task starts with no checks, `/jeeves on` suggests up to 4 from `package.json` scripts (`test`, `lint`, `typecheck`, `check`) and a top-level `Makefile` (`test`, `lint`), as `/jeeves check ...` lines to type. Nothing is added or run; script names with anything but letters, digits, `:`, `_` and `-` are not shown.
- `/jeeves history --full`: per rotation, the session's context at start and end, its cost when known, why it ended, and the handover file with its first two next actions, in plain ASCII at 50 columns. A missing or changed handover is reported, not printed. Each handover's hash is now also kept in the event log (a 0.1 task has only its latest one; older files show "hash not recorded").
- `/jeeves stats`: for this project and the current task, the number of tasks, rotations and sessions, the average context at rotation, context cleared by rotations (points, and tokens when the window is known), cost where known ("unknown" otherwise, never $0), and stops by reason. Unreadable task folders are counted as such.
- `/jeeves retry`: after a handover failed its checks (`NEEDS_REVIEW (HANDOVER_INVALID)`) it asks Claude for the handover again; earlier handovers are kept as they are. It counts toward the limit of 2 failed handovers in a row, and says so when that is used up.
- A possible rotation loop (the fresh conversation already near the threshold) now stops as `NEEDS_REVIEW (POSSIBLE_LOOP)` instead of `FAILED`: `/jeeves retry` keeps working in that conversation without a handover in it. A second loop before a rotation succeeds still stops as `FAILED`. The failure count now resets once a fresh conversation is confirmed below the loop margin, not when the continuation is sent.

## 0.1.0 (release candidate; dated when tagged)

First public beta. Release notes: `docs/release-notes/v0.1.0.md`. Release artifact: `scripts/release-zip.sh` (reproducible zip + SHA-256), built and attested by `.github/workflows/release.yml` as a draft release; GitHub Actions pinned by commit SHA.

- Security review (ST-9.1, `docs/threat-model.md`, `SECURITY.md`): values read back from `state.json` that become a file path or a git argument are checked for their exact form (ids are safe names, the start commit is hex, the handover reference is `history/handover-NNN.md`), so an edited `state.json` can no longer make Jeeves write a file through `git diff` or reach outside its folder; git runs with `core.fsmonitor` off (other commands a repository's own `.git/config` names, such as filter drivers, still run, as they do for Claude Code's own `git status`). PRIVACY.md now lists messages held during a handover.
- `/jeeves status` shows the mode (full, assisted or unsupported), the managed task if any, its state, context reading (or "unknown"), threshold, rotations, last handover or error, and the state folder. `/jeeves help` lists commands. If `/jeeves` is taken, Jeeves registers `/jeeves` and says so.
- On an unsupported Claude Code version, Jeeves says which version it needs and does nothing automatic.
- `stateDir` setting (in `/config`) chooses where task state is kept; the default is outside any repository.
- `/jeeves on [goal]` starts a managed task. With a goal, that text is saved word for word and sent as the first prompt; without one, your next typed prompt is saved word for word (`task-rev-001.md`). Slash commands are never captured. Nothing is recorded without `/jeeves on`.
- `/jeeves off` stops the task and releases its lock; no file is deleted.
- A task belongs to one session at a time: another running session gets `LOCK_HELD`. Only commands you type yourself can change a task.
- `/jeeves dod <text>` and `/jeeves check <command>` add a task revision (a new `task-rev-NNN.md`, never an edit). Verification commands are stored as text; Jeeves never runs them. `/jeeves task` shows the original prompt, every change since and the current Definition of Done. Text from Claude, other plugins or other sessions never changes the task.
- While a task is on, Jeeves reads the main conversation's context fill (the status line's figure). A missing figure shows as "unknown", never 0%, and triggers nothing. Rate-limit changes never count as context.
- The handover is requested once when context reaches the threshold (default 50%), with one warning 5 points before. Repeated or simultaneous readings past it do not request again. `/jeeves threshold <20-90>` sets it per task.
- Test runs only: `JEEVES_TEST=1` with `JEEVES_TEST_THRESHOLD_OVERRIDE=<n>` uses n% instead; `/jeeves status` then says `TEST OVERRIDE`.
- `/jeeves pause` stops any handover until `/jeeves resume`; the pause is kept across restarts. A pause while a handover is only requested cancels it; during a handover it takes effect once the fresh conversation has the task. Leaving Claude Code normally releases the task's lock, so `/jeeves resume` in the next session works at once (after a crash, after 2 minutes).
- The first `/jeeves on` on a machine explains, in three lines, where task state is kept, that a fresh conversation will start by itself, and how to pause. `/jeeves status` explains the reason code of a stopped task in one line.
- Typing `/clear` during a task pauses it (`USER_CLEAR`) and says so; `/jeeves resume` continues it in the new conversation (the task and its latest handover are sent as the next prompt), `/jeeves off` ends it.
- A disk error while saving a task revision no longer blocks later revisions.
- While a task is on, Jeeves keeps an evidence ledger of the last 200 commands (redacted, exit status) and edited files, from the main conversation and subagents. Recording never changes, delays or blocks a tool call.
- Once a handover is due, the first tool result in the main conversation adds one hidden note asking Claude to finish its current step and stop (once per rotation, never while paused).
- The handover is asked for only when Claude stops with nothing in flight: no background shell, no running subagent (scheduled crons do not hold it up). While work is in flight Jeeves waits; after 3 such stops (or 20 minutes) it pauses the task with `UNSAFE_BOUNDARY` and says why. Interrupting the handover pauses the task (`USER_INTERRUPT`). If Jeeves itself fails at a stop, Claude stops normally and no rotation step is taken.
- Redaction now also covers Stripe keys, key-like names in any case (`aws_secret_access_key = …`) and quoted secrets in JSON or YAML, and no longer masks type annotations such as `password: string`. What is caught and missed is in PRIVACY.md.
- At a safe stop Jeeves asks Claude for a handover, checks it (format, task and rotation ids, size, no secrets, files named as verified exist, branch and HEAD match git, no "passed" claim for a command whose last run failed) and saves it once as `history/handover-NNN.md`, verified by SHA-256, plus a copy in `handover.md`. An invalid handover gets up to 2 retries with the exact problems listed; after that the task stops with `NEEDS_REVIEW` (`HANDOVER_INVALID`) and earlier handovers stay untouched. 
- After the handover turn ends, Jeeves runs `/clear` once (never `--resume`, `--continue` or a fork), and only after checking that the saved handover still matches its SHA-256; a changed file stops the task with `NEEDS_REVIEW` instead. If `/clear` is refused, the handover is kept and the task waits (`ROTATE_UNAVAILABLE`).
- When context crosses the threshold while Claude is idle, Jeeves sends one short prompt ("Jeeves: prepare handover") so the handover starts without waiting for you. An interrupted turn is never nudged.
- At its own `/clear` Jeeves records the ending session once in `sessions/NNN.json` (id, start and end time, context % at start and end) and hands the task and its lock to the fresh conversation. A `/clear` you type while a handover is saved but not yet used pauses the task instead (`USER_CLEAR`).
- The fresh conversation starts with the original task (word for word), its Definition of Done and checks, and the latest handover (re-checked against its SHA-256). Jeeves then sends a continuation prompt by itself, generated from the handover: what was completed, which files changed, which checks ran with what result, what not to repeat, and the exact next actions. No keystroke is needed. If the handover cannot be verified at that point, or the prompt is refused, nothing continues and the task stops for review.
- A message you type while a handover is under way is held, not sent to the old conversation: Jeeves says so, empties the prompt box, and quotes your message word for word in the fresh conversation's first prompt. Slash commands such as `/jeeves pause` still run at once.
- Safety limits: a fresh conversation that is already near the threshold stops the task (`POSSIBLE_LOOP`) instead of rotating again; after 10 rotations a task pauses (`MAX_ROTATIONS`); after 2 failed handovers in a row the next one stops the task (`FAILED`). A rotation that continues resets the failure count.
- Assisted mode: when Claude Code refuses a plugin's `/clear` (or the task already fell back once), Jeeves keeps the verified handover, says "Run /clear, then type /jeeves continue", and `/jeeves status` shows `mode: assisted`. `/jeeves continue` works only in a fresh conversation and continues the task there. The README explains the modes.
- `/jeeves rotate` hands over now, through exactly the same steps as the threshold (handover, checks, `/clear`, continuation). Typed while Claude is idle, it sends the same one-line "prepare handover" prompt to get there.
- Completion: while a task is on, Claude's instructions include a `JEEVES-COMPLETE` block to end the task with. Saying "done" never completes it. The block counts only when every verification command (`/jeeves check`) ran with exit 0 after the last edit and no blocker is listed: then the task is `COMPLETED`, with a one-line summary (rotations, sessions, checks), its lock released and no further rotation. Missing checks get one reminder listing them; still missing, the task stops with `DOD_UNMET`. A task without verification commands always stops there, and `/jeeves done` confirms it (recorded as your decision, not as verified).
- `/jeeves dod` and `/jeeves check` can be typed right after `/jeeves on`, before your first prompt; they are saved as task revisions right after it.
- Jeeves now also reads the context fill after every tool call in the main conversation, so a long turn that fills context is caught mid-turn (the engine reports context only now and then during a turn). Readings use the exact token count, not the rounded percent.
- API errors: when a turn ends on a rate limit, login, billing, overload or other API error, the task pauses with its own code (`RATE_LIMIT`, `AUTH`, `BILLING`, `OVERLOADED`, `API_ERROR`) and a message that says what to do (for a rate limit, when it resets, if Claude Code knows). Jeeves never retries or sends a prompt by itself after one; `/jeeves resume` continues. Such a pause does not count as a failed rotation.
- Compaction (ADR-006): while a task is active, Claude Code's compaction ahead of time (`precompute`) is skipped. `/compact` and automatic compaction are never blocked; after one, Jeeves hands the task over to a fresh conversation (`COMPACTED`), because a compacted context is lossy.
- `/jeeves recover` continues a task that an earlier session left behind (a crash, or leaving Claude Code mid-task), once, in this conversation: the task and its last validated handover go in as the next prompt, with a note to check the repository first when work after that handover may exist. A handover saved just before a crash is picked up even if its state change was lost. Never while another running session owns the task (`LOCK_HELD`, with how long to wait). An unreadable `state.json` is rebuilt from the task's files (the old one is kept). At start, Jeeves names such a task once; the `autoRecover` setting recovers it by itself. The README has a Troubleshooting section.
- Disk errors and moved repositories: when Jeeves cannot write its task files, the task is blocked (`DISK`) with the folder and the fix, the last saved state is kept, and `/jeeves resume` continues once the disk works. Jeeves never continues a task on another branch than its last handover's (`REPO_MISMATCH`): switch back, or confirm with `/jeeves recover --relink`. A repository folder that was moved is found from the new folder by its old path and moved over with `/jeeves recover --relink`.
- Several sessions: a second running Claude Code in the same project that types `/jeeves on` starts its own separate task; the first session's task stays its own (`LOCK_HELD` for any change from elsewhere). Worktrees and other repositories always have separate tasks.
- Test runs only: `JEEVES_TEST=1` with `JEEVES_TEST_CRASH=<point>` stops Jeeves dead at a named point of a rotation, for the crash matrix (`npm run crash:report`).
- The handover instruction now asks Claude to name each file in a `[verified]` bullet by its real path from the repository root, never a placeholder or a `../` path (the checks reject those).
- The command is now `/jeeves` (it was `/relay`), matching the product name. If another plugin or command already owns `/jeeves`, Jeeves registers `/relay` instead and says so.
- Status entry and transition lines: while a task is on, Jeeves keeps one entry in the status area under the prompt (`Jeeves 34%/50%` while watching context, `?` when the figure is unknown; otherwise the state in words, such as `Jeeves: writing handover` or `Jeeves: paused (USER_PAUSE)`), never more than 40 columns. Your own status line is left alone. Each state change adds one dim line to the transcript (`Jeeves: handover requested (THRESHOLD)`, `Jeeves: handover validated, starting fresh`, ...); these lines are not sent to Claude, and tool calls never add one.
- `/jeeves history` lists the task's last 20 state changes (time in UTC, from > to, reason code, context %) and a summary of rotations, sessions and failed handovers, each line within 80 columns. It only reads, and works after `/jeeves off` too.
- `/jeeves status --diagnose` prints a report to paste into a bug report: Jeeves and Claude Code versions, mode and any missing capability with a hint, OS, state folder (where it came from, writable or not), git, the task and its lock. Your home folder is shown as `~`, session ids are shortened and known secret formats are redacted. `docs/compatibility.md` lists the Claude Code versions tested (`npm run compat`).
- Install from the repository's marketplace (`/plugin install jeeves --marketplace nickycdk/jeeves`, or a clone's path). Uninstalling removes only the plugin's settings entry; task files stay until you delete them. `/jeeves purge --task <id> | --project | --all` lists the folders it would delete and deletes them only after `/jeeves purge confirm <code>` within 2 minutes; a running task is never deleted.
- Documentation: the README now covers the problem, requirements, install/update/uninstall, a quickstart, what Jeeves does by itself and when it stops, modes, data and privacy, every command and setting with its default, and an FAQ; plus `docs/troubleshooting.md` (every stop reason with what to type) and `docs/architecture.md`. CONTRIBUTING lists every script; issue and pull-request templates and a code of conduct were added.
