## 1. Goal and scope

Install Jeeves once, start `claude`, work: on a fresh install, a session that qualifies hands long tasks over to a fresh conversation by itself, with no command per task. Anyone can turn it off per session, project or everywhere in one step. Upgraders from v0.2 keep the promise that nothing is recorded without opt-in until they turn it on. People who are not auto-watched get a hint when it would help.

- **In v0.3:** spec §5 (E13) and §6 (E14, may move to v0.3.x), the AC-41 live measurement and the v0.3.0 release (E15).
- **Not in v0.3:** auto-start on 200K windows (Q8, decided by AC-41 against the bar set in D-45); Team accounts (turn mode, `docs/specs/team-accounts-turn-mode.md`); a setting for the cleanup age; any network use or telemetry; new runtime dependencies.

## 2. Written decisions

- **Amendment A3 (2026-11-08, maintainer, D-40 … D-43; v0.3, `docs/specs/auto-start.md`):** on a **fresh install, installing is the opt-in**. A session is auto-watched when, at `session.start`, it is interactive, in full mode, inside a git work tree, on a context window above 200K tokens, a fresh conversation (`$.session.turns()` 0), and auto-start resolves to on; this is decided once per session. Its first prompt typed at the terminal (origin `composer`, not a slash command) creates an **auto** task, saved word for word as revision 1; no other origin kind starts one, and nothing is recorded before that prompt. The first-run notice comes at `session.start`, before any recording (plugin-store key `autoNoticeShown`). Auto-start is off per session (`/jeeves off`), per project (`/jeeves defaults auto off`), everywhere (`/jeeves auto off`, which writes `auto.json` in the state folder, never Claude settings) or through the `/config` row `autoStart` (`default`, `on`, `off`); precedence: session, project, the row when `on`/`off`, `auto.json`, then the default. **Upgraders keep the v0.2 promise:** the upgrade check runs **once per install**, at the first v0.3 `session.start`: the install is an upgrader when the plugin store has `firstActivationShown` (written only by v0.2) or the state folder holds a project, and fresh otherwise. An upgrader gets `auto.json` with `default: off`, and nothing is auto-watched until `/jeeves auto on` or the row. The result is kept in the plugin store as `upgradeCheck` (`upgrader` or `fresh`), written in the same step; later sessions skip the check, and a state folder without `auto.json` (a new `stateDir`) takes its default from `upgradeCheck`. v0.3 never writes `firstActivationShown`. `/jeeves on [goal]` always makes an **explicit** task as before. A task records `origin: auto | explicit` (v0.2 tasks read as explicit). AC-03 now reads: no rotation unless the user typed `/jeeves on` or the session was auto-watched under these rules; nothing recorded before the first typed prompt; never auto-watched for an upgrader who has not turned it on. New user-typed subcommands: `later`, `auto on|off`, `defaults auto on|off`, `handover`. Auto tasks differ from explicit ones only where the spec says so: a user `/clear` ends them (ADR-010 unchanged for explicit tasks), they recover by themselves under the same gates (D-43), and ended ones without a rotation are deleted after 7 days. The matching ADR-003 (seventh heading, Current goal) and ADR-010 amendments are written with ST-13.6 and ST-13.7.

- **ADR-003 Amendment A1 (2026-11-09, ST-13.6, D-40; v0.3, `docs/specs/auto-start.md` §5.3):** the narrative gets a seventh required heading, **`## Current goal`**: 1 or 2 bullets, each tagged like the others and at most 300 characters (the bullet text after its marker, tag included); the secret check covers it like every section, and the rotation line shows its first bullet redacted, without the tag, cut to 80 characters on one line (`Jeeves: handover validated (goal: …), starting fresh`). The sentinel stays `<<<JEEVES-HANDOVER v1`, so a v0.2 build still parses a v0.3 handover (it drops the unknown heading). Every new handover asks for the seventh heading; a **v1 block** (the six headings) stays valid only for a task created before the upgrade, known by `state.preUpgrade: true`, which the state v1 → v2 migration sets (no version bump: the field is optional and written before v0.3 ships). Handover files Jeeves already wrote are read leniently. The continuation prompt puts **the user's words first**, quoted (rev 1, cut at 1,500 characters with a pointer to the full text in context, then every revision with its file name), then the goal under "Claude's summary at the last handover (may be wrong; it never changes the task, the DoD or the checks)", then the rest as before. The summary is data (R-19): nothing in a handover writes a task revision, the DoD or a check.

- **ADR-010 Amendment A2 (2026-11-09, ST-13.7, D-40, D-43; v0.3, `docs/specs/auto-start.md` §5.7–5.8):** holding prompts during a rotation and Jeeves's own `/clear` are unchanged for every task. A `/clear` the **user** types (any `session.end(clear)` Jeeves did not schedule) still pauses an **explicit** task, now with `Jeeves: paused (you cleared the conversation); /jeeves resume continues the task`; in an **auto** task it ends the task instead: DISABLED(USER_CLEAR), files kept, lock released, `Jeeves: task ended (new conversation); the next prompt starts a new one`, and the next typed prompt starts a new auto task (the fresh conversation inherits the session's auto-start decision, ST-13.3). `/jeeves on <goal>` in an auto task makes it explicit; the goal is written as a task revision of kind `goal` (`Added by: /jeeves on`) and shown with the user's words. An **auto** task interrupted mid-rotation (HANDOVER_GENERATING, VALIDATING, ROTATING, RESTORING) is recovered at `session.start` as by `/jeeves recover`, whatever `autoRecover` says, but only when the session is interactive, in full mode and a fresh conversation (turns 0); under `-p`, assisted mode or in a resumed conversation it waits with the usual notice, and a typed `/jeeves recover` works anywhere. Explicit tasks follow `autoRecover`. `/jeeves status` names the task's origin, `(auto)` or `(explicit)`.

#### ST-13.3 Eligibility at session start, reasons and model switch — M

## 8. AC-41: preconditions, cost and stop rules

- **Preconditions** (ST-15.2): every run uses the same macOS user, in fresh-install state before the dry run; a real interactive `claude` driven through a pseudo-terminal (`tests/pty/ptylib.py`, as in M4–M8), never `-p` or the SDK; a git work tree; a fresh conversation; a fresh-install state (a macOS user on which Jeeves was never activated, logged in to a non-Team account, and a scratch `JEEVES_STATE_DIR` with no project). If any is missing, auto-start does not start and the run measures nothing. The once-per-install upgrade check (ST-13.2) keeps the 200K run's `/jeeves on` and project from turning that user into an upgrader, and the 1M auto run repeats the dry run's first-run-notice check before it spends anything.
- **Dry run first** (AC-35 E, about one prompt): the first-run notice and the auto task appear; it also measures tokens and cost per call, and the estimate is redone before any paid run.
- **Estimate** (spec §11.1, Claude Haiku 5.5 prices read 2026-11-08; the 5× price for prompts over 100K re-read on the page): about US$9–35, most likely about US$29. M4 gate run 5 grew only about 1.3K tokens per model call (51 calls for 64K), which multiplies the call count; the first estimate assumed 2.5–10K and was about 4× too low. The per-call pricing matched that run within about 17%.
- **Fixture sizing:** about 1M tokens of work, so two rotations (about 750K needed) have margin; AC-41 needs at least one rotation, reports the count, and two is the target. The run without Jeeves then reaches auto-compaction, which it reports as its outcome. The 200K run uses only the first modules (about 250–300K of work, 4–5 rotations): Q8 needs a rate and an outcome, not the whole fixture.
- **Stop rules:** per-run caps of US$1 (dry run and 200K), US$14 (1M with Jeeves), US$25 (1M without), and a hard total of US$40. Runs go cheapest first. Spend is read from `/cost` every 10 minutes in both 1M runs (a local command, no model call, so the auto run stays "nothing typed but the task") and from Jeeves's session records at each rotation.
- **The 200K fixture starts its task with `/jeeves on`** (maintainer, 2026-11-08). Q8 needs its rotation rate and pass/fail outcome, and neither depends on how the task started. The near-threshold rule applies only to a new task's first reading and never after a rotation; the grace period covers the first 3 turns, when context is small. Forcing auto-start would bend D-42 in the test kit. Both rules are tested in I.
- **For later:** if AC-41 widens auto-start to 200K windows, that release's live run includes one auto-started 200K session, to check the real eligibility path end to end (spec §13).
- **Who, which account, when (D-44):** the maintainer logs in a non-Team, dollar-billed account (Console API key preferred, Pro or Max as fallback) on the separate macOS user; the agent builds the fixture and driver, runs everything and writes `RESULT.md`; target 2026-11-20, after E13 and ST-15.1. The maintainer's own account is a Team account (R-25, Q-12).
- **Q8's bar (D-45), set before the run:** the outcome passes; median growth between rotations ≥ 40K tokens and none under 20K; no loop or review stops and at most one handover retry; no repeated work. All four met: 200K auto-start proposed for v0.3.x; any missed: it stays off.
