# ST-13.1 / AC-45: what a v0.2.0 build writes into a state folder v0.3 has used

**Date:** 2026-11-08 · **Source audited:** `jeeves/src` and `jeeves/hooks` at commit `5916cc1` (the 0.2.0 tree; `src/core` byte-identical to `tests/fixtures/v0.2-core/`) · **Layer:** U (`tests/unit/downgrade.spec.ts` against the frozen v0.2 reader) plus this audit. No whole v0.2 build was run against v0.3 files (no I or C layer).

**Question:** the frozen reader shows v0.2 refuses v0.3 files when it reads them. AC-45 also says v0.2 rewrites nothing, which needs every v0.2 write into the state folder to go through a successful read first. Every write was listed with `git grep` for the storage and port write calls (`writeState`, `replaceFile`, `appendEvent`, `writeImmutable`, `acquireLock`/`takeoverLock`/`releaseLock`/`heartbeat`, `ensureRoot`, `port.write`, `rm`/`cp`/`mv` through `port.run`) and traced to where its folder comes from.

**What v0.3 changes on disk:** `state.json` schema 2 (every task v0.3 creates or writes), project `config.json` schema 2 only while `autoStart` is set, a new `auto.json`. Events, sessions, locks, `project.json` and the immutable files keep their v0.2 format.

| v0.2 write | Where (0.2.0) | Folder or file comes from | Against v0.3 files |
|---|---|---|---|
| `writeState` in a transition | `adapter/task.ts:71`, `:100` | a task from `projectTasks`, which keeps only states that parsed (`r.ok`); a `SCHEMA_TOO_NEW` task goes to `broken` | never reached for a v0.3 task |
| `appendEvent`, `releaseLock`, session record (`writeImmutable`) from effects | `adapter/effects.ts:30`, `:40`, `:43` | the same transition, on the same parsed task | never reached |
| `claim` → `acquireLock` / `takeoverLock` | `adapter/task.ts:158`; callers `commands.ts:122`, `:143`, `recover.ts:188` | targets picked from parsed tasks (`commands`) or from moved tasks found through parsed states (`relinkHere`) | never reached |
| heartbeat, `releaseLock` on session end | `adapter/task.ts:273`, `:325`, `:338` | the session's own task, or parsed tasks whose `activeSessionId` is this session | never reached |
| task revisions, facts snapshot, handover files, `handover.md` | `adapter/task.ts:229`, `:247`, `:291`, `:398`, `:499`, `:501` | the session's own (parsed) task | never reached |
| `/jeeves recover`: `removeOldTmp`, `rebuild` (copy, `writeState`, `appendEvent`), `releaseLock` | `adapter/recover.ts:67`, `:80`–`:100`, `:141`–`:147` | candidates; a `SCHEMA_TOO_NEW` task is classified `too-new` (`core/recovery.ts:36`) and only answered with "update Jeeves; nothing was changed" (`MSG.recoverTooNew`); `rebuild` runs only for `rebuild` (a corrupt file, not a newer one) | never reached |
| new task: `mkdir` lock, `task-rev-001.md`, `writeState` | `adapter/task.ts:185`, `:190` | a new task folder with a new id | no v0.3 file touched; see note 1 |
| `project.json` (`replaceFile`) at task start | `adapter/task.ts:203` | the project folder | same format in v0.2 and v0.3 (schema 1); rewritten with the same fields |
| `defaults threshold` / `defaults check` | `adapter/defaults.ts` | `config.json` | refused while the file is unreadable to v0.2 ("never overwrite it"), so a schema-2 file is kept |
| `defaults clear` | `adapter/defaults.ts:41` | `config.json` | **writes over a schema-2 file**: user-typed, it is v0.2's documented way out of an unreadable file. Loses the project's `autoStart` and any threshold or checks in that file; see note 2 |
| `/jeeves purge` (`rm -rf`) | `adapter/purge.ts:32` | task or project folders named by the user, confirmed with a code; tasks with a live lock are skipped (decided by the lock, so it covers unreadable tasks) | **deletes v0.3 tasks too**: a user-typed, confirmed delete, not a rewrite |
| `ensureRoot` (`mkdir -p`, `chmod 700`) | `adapter/storage.ts:98` | the state root, only when it does not exist | nothing to touch |
| `auto.json` | (none) | v0.2 has no code that names it | never read or written |

**Result:** no v0.2 write reaches a v0.3 task without a successful read, so a v0.3 task is never rewritten. The two writes that do reach v0.3 files are both typed by the user: `defaults clear` (replaces `config.json`) and `purge` (deletes). Neither is a silent rewrite, and the v0.3 release notes name both.

**Notes:**
1. v0.2 does not see a v0.3 task as live, so `/jeeves on` in v0.2 can start a second task in a project where a v0.3 task is still active. Each task has its own folder and lock, so nothing is overwritten. v0.2 shows the v0.3 task only as a warning line (`<task>: schemaVersion: version 2 is newer than this version of Jeeves supports (1); update Jeeves`) where it lists unreadable tasks, and `/jeeves recover` answers "update Jeeves; nothing was changed".
2. After `defaults clear` in v0.2, the project has no `autoStart` setting; when the user goes back to v0.3, auto-start follows `auto.json` or the default for that project.
